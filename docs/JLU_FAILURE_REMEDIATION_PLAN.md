## 1. 目标与边界

先保证已有来源稳定、数据正确，再扩大覆盖。完成标准是每项都有可复现结论：已修复、有效空栏目、范围外引用、站点/环境受阻或仍未验证。不能为了清零失败，把受限来源标为已支持。

60 个曾失败/权限受限栏目目前按证据分为：27 个导航风险已拦截、8 个已改善但部分通过、6 个日期含义待确认、11 个空结果待复验、7 个访问/链接受阻、1 个明确权限限制。它们不是 60 个当前故障；15 个发现阶段受阻站点与此有重叠。附件、分页、重复候选采用独立口径，不与栏目数相加。

本计划默认只修改必要解析/验证代码、独立候选和报告。19 个 B4 候选继续禁用；不批量改正式 `sources.yaml`，不写正式 SQLite，不迁移/补抓历史库，不改系统代理或路由，不部署 Cloud、不安装客户端、不提交 GitHub 或发布 Release。真实 Cloud 缺少可用验证环境时，完成其余工作并明确保留未验证项。

## 4. B5-B：确认招生日期含义

对象为招生通知、招生录取公示、博士招生公告、博士录取公示、硕士招生公告、硕士录取公示六个栏目，具体 URL 沿用 B4 候选和失败台账。

1. 先核对已保存的列表日期与 `.arc-info` 更新时间，以及可得的官方页面标记或说明；需要补证时，每栏至少核对三条，包含置顶/旧文和可观察到的日期冲突样本。
2. 只有明确的发布元信息才能确认为发布日期。不能用正文活动日、截止日、抓取日、更新时间推造发布日期；标准元数据也需与当前文章及可见页面对照。
3. 明确现有列表日期的来源和含义；不能因为列表/详情两个数字相同，就判定“发布”语义已确认。证据不足则继续标日期待确认并禁用，不直接迁移已有日期。
4. 有新规则才补相应脱敏 fixture 和必要测试，保持附件 DTO、列表身份和已有日期保护逻辑；不顺手新增 API/数据库字段。

验收：六个栏目逐条有日期语义依据或未确认原因；缺失日期不抹掉正式已有日期，更新日期不冒充发布。日期规则修复后复验标题/正文/附件提取，不能只测日期值。

## 5. B5-C：分页、增量与去重

先验证既有 8 个配置栏目与 B4 的 9 个内容样本通过栏目，按 URL 去重而非相加计数。OA 不可达时先做隔离控制并保留实时未验证。六个招生栏目需先有 B5-B 结论再决定是否进入准入验证。

### 分页

- 复用 Generic 的 `next_page_selector`、`pagination_limit` 和全局页数限制。StaticHTMLSource 扩展只使用显式配置，保留原缺省首屏行为。
- 单轮最多三页，并为总条数设明确上限；达到任一上限立即停止，记录实际页数、条数和终止原因。历史补抓另立范围，不在本计划自动执行。
- 对照第一、第二页的原文链接，验证禁用下一页、重复页、循环链接、跨栏目/跨域跳转和置顶旧通知。不能因首页全是旧置顶就漏掉后页新通知。
- 就业网下一页机制以实际公开页面为准；不猜 API、分页参数或未经确认的请求协议。
- 验证抓多页后不会又截断成仅首页数量；分别报告页面访问量、去重通知量和被条数上限截断的范围。

### 增量和用户状态

- 用独立数据库构造原有通知、来源关系、已读、收藏及 baseline，连续执行两轮；第二轮对未变化数据不重复新增。
- 模拟标题恢复、日期纠正、附件补齐、图片链接增加、单条失败及后续恢复。保留 notice ID、来源归属、用户状态与成功 baseline；失败不推进该条成功状态。
- 对照原审计 113 组同 URL、48 组同标题/日期候选，先复现再分类：同一通知的栏目引用、跨站转载、协议别名、真正重复。保留 public_id 和 canonical URL，不全局放宽相似阈值。
- 标题/日期不变但旧正文或附件缺失的情况单独记录现有增量跳过边界；如需历史重验，仅给可审查方案，不批量回写正式库。

验收：分页边界可复现；两轮隔离抓取无重复新增或错误合并，用户状态保持；已检查的正常来源没有内容回归。没有实际验证历史范围时不得宣传全历史覆盖。

## 6. B5-D：附件与真实运行环境准入

### 附件

- 先复用 25 个已有探测端点的证据：17 个验证码、1 个 robots 限制、7 个文件前缀。已确定受限的入口在无条件变化时不重复请求。
- 对原 108 个带附件问题标签的栏目，按待准入来源优先分批补证；不是一次探测 108 站或下载全部附件。每栏先核对一个有附件详情及一个入口，其余继续未检查。
- 可见附件数量、名称、完整 URL 和类型对照原页面；PDF/Office 等明确附件需提取，logo、导航和正文图片不能混入附件。
- 文件探测沿用最多 4 KiB；HTML/验证码/认证、失效链接、类型冲突分别记录。只取得文件前缀就只声明前缀验证，不承诺完整下载。
- 验证码和访问规则受限保留原合法入口。若该来源允许“可提取、需用户按原站流程下载”，在准入矩阵写明这一能力边界；不能记为自动下载支持。

### 环境

分别记录 Windows 本地公开抓取、实际 Cloud Linux 抓取、Cloud feed 以及 Desktop fallback。保留现有 `cloud_preferred / cloud_only / local_only`、ownership、source identity、订阅和安全边界。

本地 Fake-IP/系统代理结果不能替代 Cloud DNS/IP/peer 校验；Cloud feed 未配置不算云失败，也不算云抓取成功。没有可用 Cloud 环境时记录未验证，不新建部署、不改系统网络。任何本地恢复都不能自动改成云支持。

验收交付为逐来源矩阵：内容、日期、分页、重复刷新、附件能力、执行环境及用户状态分别有证据。结论分为“满足指定环境准入条件”“有能力限制”“受阻”“未验证”。本计划仍不正式启用来源；正式变更须另有明确范围，逐条审查而非批量导入候选。

## 7. B6：空列表和导航风险逐批处理

优先处理 11 个原空结果中属于 P2 的 8 个入口：药学院学院通知，以及白求恩第三临床医学院的 7 个候选。医院候选包含单篇停电通知，须先确认其目标性质；单篇引用有证据时另行排除，不强行当栏目适配。

其次处理 27 个已拦截导航风险的学院部分：先确认官方现行栏目路径，区分“真实零条”“旧路径”“未知模板”“索引引用”，再按实际 CMS 分组。每模板选正常、空栏目和特殊日期/附件控制；每小批 5–10 个栏目，至少三条详情核对，不足三条全检并注明。

未知模板优先用通用选择器；确实无法表达才加小型适配规则。不重新引入全页正文或导航回退。风险拦截已修复不代表来源已适配，零条也不能当抓取成功。

验收：每个入口有明确性质、证据和候选配置；适配样本覆盖标题、日期、正文、附件及有界分页。新模板依赖的 B5 安全/去重规则必须通过，现有来源不得回归。

验收：确认的新入口有官方依据、规范化/别名依据和验证范围；剩余缺口逐条说明原因，不能以外部受阻未消失为由伪造通过或无限重试。

## 9. 全程执行规则与最终验收

- 网络任务单进程串行，共享 HTML/附件限速状态；审计入口全局至少 1 秒、同源至少 1.2 秒，遵守更长 Crawl-delay。瞬时超时/502/503/504 最多两次尝试；权限、验证码、403/429、robots 禁止及确定性证书失败立即停止。
- 每次修改前保存隔离基线，先跑与真实缺陷相关的 fixture、安全及持久化回归，再跑完整后端测试，记录实际通过/失败/跳过。只改计划文档的本次不重复运行测试。
- 每条结论保存 URL、机构/栏目、原抓取时间、复核时间、原因、快照/有限前缀 SHA、代码/配置指纹和执行环境；实时、离线重放和 MockTransport 明确分开。
- 原审计和 B1–B4 报告不覆盖，用户未提交改动不 reset/clean；回滚只针对本子批自己的规则/候选，不重置数据库。任何既有来源回归、安全边界变弱或用户状态变化，停止扩展并先修复。
- 不涉及 UI；确有 UI 需求时另行遵守 Design Contract 和双尺寸、前端 test/lint/build 验证，不借适配改页面或 API 契约。

最终交付包括逐条处置台账、各批报告、独立候选、隔离回归及逐环境准入矩阵。每个问题要么有修复证据，要么有明确外部阻塞/未验证范围；“失败清零”“HTTP 200”“非空预览”均不作为完成标准。
